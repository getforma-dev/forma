# FORMA-301 acceptance and evidence matrix

2026-10-26. **Rows distinguish design verification, partial experimental evidence and future qualification.** This is an executable-work backlog and proof definition, not a report of successful implementation. Research prototype results are historical inputs only. The [research map](research-map.md) explains why each behavior matters; the [JSON form](research-map.json) contains reverse question references.

## Gates and receipts

- **Design:** traceability/provenance and accepted contracts.
- **Proof:** real typed native routes, policy/adoption/form behavior and three-engine feasibility before production integration.
- **Qualification:** the packed implementation and full supported contract.
- **Pilot:** bounded application/hosting exercise after qualification; never a substitute for it.

For each execution retain the test ID, full source SHA and diff/dirty state, artifact hashes, exact command, relevant toolchain/browser version, timestamps, result, raw log/trace, and any scope limitation. A skipped/unsupported assertion is not a pass. Negative controls must fail for the intended reason. Normal native navigation must explicitly assert zero document reloads; fallback success is recorded separately. Do not overwrite failed runs when rerunning.

## Minimal first proof campaign

The initial two-route fixture targets RT-N01–N05, RT-O01–O03, RT-S01–S05, RT-C01–C02, RT-H01, RT-L01, RT-F01 and F03–F09, RT-X02, RT-A01–A02 and RT-A05. Current execution covers the subsets recorded above; this list is not a pass claim. Tests requiring integration must use the actual built compiler, Rust renderer and core product rather than a fake DOM-only transport. A small unit proof can precede this campaign, but is identified as such.

Include a persistent layout input and distinct page islands. Hold responses and deferred activations deliberately. Mutate server data through one real handler, submit invalid data without losing safe entered values, then submit valid data and prove fresh props. Navigate during a held POST; lose a response after server handling and count client transmission attempts. No client-only test can establish exactly-once server execution.

## Prospective measurement protocol

Before RT-M01/M02, the main design records fixture route count/shape, complete group contents, payload size, device/CPU/network profile, warm-up and sample count, measured percentile definition, and numerical acceptance budgets. Existing gates stay unchanged. Mark budgets as prospective; a missed result remains a failure and can prompt a separately reviewed decision, not an edited historical threshold. RT-O02 is deterministic resource-count acceptance; RT-M03 supplements it with noisy browser heap observations and must not turn a single heap snapshot into a no-leak claim.

## Explicit later work

Independent keyed/background fetchers, general private HTML/data caches, progressive streaming (FORMA-226), cross-route lazy JavaScript transport/discovery, Angular named outlets/matrix parameters, arbitrary persistent custom-element/media transplants and visual transition choreography are not first-release acceptance. Their research rows remain traceable. Ordinary no-JavaScript and documented unsupported-destination behavior are current requirements, not deferred work.

Proof receipt paths resolve through evidence/implementation-report.md; qualification-only rows remain unexecuted. The implementation contract is api-protocol.md and fixed measurements are in measurement-protocol.md.
