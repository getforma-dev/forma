# Failed P17 diagnostic retention

The original workflow at5eef0c0e6fc8eba368e1be6bc7aaf76abe1af17a skips its P17 artifact upload after the verifier exits unsuccessfully, losing the actual partial/security/performance reports saved by the verifier. The new source regression parses that actual YAML and fails because the upload has no failure-retaining condition. The original workflow and validator are byte-exact Git originals.

The correction permits `always()` only on the exact pinned `verify` upload of `release-p17`, with the same path, overwrite and missing-file error policy. The verifier stays fail-fast; its authenticated hash-record step still runs only after success. Publishers still require successful `verify`, have no failure-overriding status function and retain the exact tag conditions and permissions. A successfully uploaded partial report therefore remains failure diagnostics, not a release success record. This follows GitHub's [implicit success/status functions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions) and [job dependency rules](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds).
